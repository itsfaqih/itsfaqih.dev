Handling Timestamps

Store and send UTC. Turn it local only on the reader's screen.

Convert picked times to UTC in the browser, return ISO strings ending in Z, and filter by the user's own day as a UTC range.

LOCAL→UTC

One moment, two clocks

Keep one moment as one value until it reaches the screen of Rina in Jakarta (UTC+7) or Sam in New York (UTC−5).

Store the moment in UTC

Rina in Jakarta and Sam in New York order in the same second. A column with no offset stores each writer's local time, so one moment becomes two values. Store UTC to keep it one.

UTC never shifts for daylight saving or politics. It means the same moment everywhere.

Return it with a Z

An ISO string without a Z has no zone, so each browser reads it as local time. Rina and Sam both see 6:00 AM, and both are wrong. End it with a Z so each browser converts it to its own zone.

Send the zone with the input

Rina sets a reminder for 7:00 AM. From 2026-01-01T07:00:00 the server can't tell whose 7:00 that is, so it reads it as UTC. Send UTC with a Z, or the local time with its offset. Both name one moment.

Filter by the user's day

Rina asks for her orders on Jan 10. Her day starts at midnight in Jakarta, 17:00 UTC the day before, so send that moment. If you send midnight with no zone, the query runs 07:00 to 07:00 her time, so orders before 07:00 go missing and the next morning's show up.

TL;DR

  1. Saving a timestampStore UTC, with no offset column
  2. Returning one from the APIReturn ISO 8601 ending in Z
  3. Showing it to someoneFormat it in their browser
  4. Sending a time the user pickedConvert to UTC, or keep its offset
  5. Filtering by a dateSend the user's day as a UTC range
  6. Date mathDo the math on parsed times, never on the string
