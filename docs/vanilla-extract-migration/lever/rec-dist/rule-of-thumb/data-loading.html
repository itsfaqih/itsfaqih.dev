Data Loading

Fetch early, show what you have, and never blank the screen.

Start requests on navigation and keep stale data on screen. Show a skeleton only after 200ms.

STALEFRESH
BLANK→INSTANT

Fast first paint, smooth updates

Design the wait, because people judge loading by what they see while it lasts.

Start fetching early

Fetch on navigation, not on render. A fetch that starts when the page renders waits for the page's code to load and render first. Start it as the user navigates, so it runs while the code loads. Wait for what the page needs and stream the rest.

Errors where the data was

Show the error where the data would go, with a Retry button. A toast fades before anyone reads it and leaves an empty card. Log every failure so you hear about it before your users do.

Parse at the boundary

API data is a guess until you check it. Parse it as soon as it arrives and give optional fields a fallback, so the rest of your code gets real types. If you skip it, a missing field crashes far from where it came in.

When a required field fails, show a plain message and log the details. Update the schema when the API changes. It documents the API too.

Persist what can't mislead

A disk cache is already old when the app next opens. Persist history, settings and static content, and show when it was updated. Never persist balances, prices or stock counts. A stale number there leads to a wrong decision.

TL;DR

  1. SEO or first paint mattersRender it on the server. Behind a login, the browser is fine
  2. Data a page needsStart it on navigation, batch it, stream the rest
  3. Refetching data you haveKeep it on screen with a small spinner
  4. A reply that may be quickShow loading UI only after 200ms
  5. A request that failsShow the error in place, with Retry. Log it
  6. Updates within a secondPush them over a live connection. At 30s or slower, poll
  7. Anything from an APIParse it where it arrives
